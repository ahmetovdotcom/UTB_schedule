# Один Docker Compose для двух приложений

- **Студенты:** `https://okak.asia`.
- **Сотрудники:** `https://app.okak.asia`.
- **Локально:** `http://localhost:8080` и `http://localhost:8081` соответственно.

Один запуск поднимает 6 контейнеров: два FastAPI backend, два Vue/Nginx frontend,
PostgreSQL и Caddy.
SQLite сотрудников хранится в отдельном volume. PostgreSQL и API не публикуют
порты на хосте. Публикация идёт между API по закрытой Docker-сети; запись через
публичный студенческий сайт заблокирована. Caddy получает и обновляет TLS-сертификаты.

## Структура

Две папки должны лежать рядом и называться именно так:

```text
projects/
├── timetable-system/
│   ├── backend/
│   ├── frontend/
│   └── deploy/       ← запуск отсюда
└── UTB2/
    ├── backend/
    └── frontend/
```

Нужны Docker Engine/Desktop с Compose v2, Bash и OpenSSL. На Mac откройте
Docker Desktop и дождитесь его запуска. Python 3 нужен только для команды
`package`, чтобы собрать переносимый архив; сами приложения работают в Docker.

## Первая проверка на ноутбуке

```bash
cd /Users/amirahmetov/timetable-system/deploy
./deploy.sh init
```

Команда создаёт `deploy/.env` со случайным паролем PostgreSQL и общим ключом
публикации. Повторный запуск сохраняет существующие значения. Если `.env` отсутствует, но
Docker volumes этой установки уже существуют, `init` откажется генерировать новые
пароли: перенесите `.env` из предыдущей папки или `deploy.env` из резервной копии. Этот `.env` отдельный
от локальных `.env` обоих backend: контейнеры используют **только deploy/.env**.
Нельзя менять пароль уже созданной PostgreSQL просто редактированием `.env`.

### Если нужно использовать нынешнее расписание

**До первого `up`** импортируйте текущую SQLite БД сотрудников:

```bash
./deploy.sh import-staff ../backend/timetable.db
```

Эта команда делает согласованную копию SQLite, включая подтверждённые изменения из
WAL, и не меняет исходный файл. Она откажется заменять уже существующую БД Docker.
Выберите правильный файл: в проекте есть также `../timetable.db`; обычный запуск
`backend/run_dev.py` использует именно `backend/timetable.db`.

Если ранее запускали Docker с пустой БД, не удаляйте volumes вслепую: сначала
сохраните нужные данные. Для независимой чистой установки можно выбрать другое
имя проекта через `COMPOSE_PROJECT_NAME` в `deploy/.env`.

### Запуск

```bash
./deploy.sh up
```

Откройте:

- студенческий сайт: **http://localhost:8080**;
- кабинет сотрудников: **http://localhost:8081**.

Если импортировали БД, сохранённые в ней учётные записи тоже перенесутся. Для
создания новой учётной записи или смены пароля:

```bash
./deploy.sh user admin
```

Пароль вводится скрыто. Ни логина, ни пароля по умолчанию нет. Если начали с
пустой БД, заполните справочники и расписание. Нажмите «Опубликовать для студентов»
и обновите студенческую страницу — появятся группы и пары. До первой публикации
студенческий сайт пустой. Тестовые данные автоматически не добавляются.

Если порты заняты, поменяйте `STUDENT_PORT` и `STAFF_PORT` в `deploy/.env`.
Локальный режим слушает только `127.0.0.1`, допускает HTTP cookie и не требует DNS.
Обычные процессы на 5173/8000 запуску не мешают. Прежний отдельный UTB2 на 8080
нужно остановить или выбрать другой `STUDENT_PORT`.

## Перенос на сервер

### 1. Подготовить архив на ноутбуке

```bash
./deploy.sh package
```

Архив в `deploy/releases/` содержит оба приложения и этот комплект запуска.
В нём **нет паролей, `.env`, баз, node_modules, venv и Git-истории**. Архив исходников
одинаково подходит для ARM Mac и x86-64 сервера — образы собираются на целевой машине.
Не переносите Docker volumes простым копированием между архитектурами.

Если хотите перенести данные из локальной Docker-установки:

```bash
./deploy.sh backup
```

В `deploy/backups/<дата>/` появятся `staff.sqlite`, `students.dump` и `deploy.env`.
Команда ненадолго останавливает API сотрудников, чтобы во время копирования не
шла публикация, затем запускает его обратно. Эти файлы содержат приватные данные
и секреты. Храните и передавайте их отдельно от публичного архива кода.

### 2. Настроить DNS и доступ

Создайте A-записи `okak.asia` и `app.okak.asia` на публичный IPv4 сервера.
Если есть AAAA-записи, они тоже должны вести на этот сервер с рабочим IPv6;
иначе уберите их. Откройте входящие TCP 80/443; UDP 443 нужен для HTTP/3, но не
обязателен для обычного HTTPS. Другие порты базы/API открывать не нужно.

Если `okak.asia` уже работает на этом сервере, предварительно сохраните его БД
и настройки. Остановите прежний Nginx/Caddy/контейнер, занимающий 80/443, только
когда будете готовы переключаться. Новый Compose не переносит старый PostgreSQL
volume автоматически. Для сохранения существующих студенческих ID восстановите
его дамп до первой публикации (порядок ниже).

### 3. Развернуть

Установите Docker Engine и Compose v2. Загрузите архив на сервер, затем:

```bash
mkdir -p ~/okak
cd ~/okak
tar -xzf /путь/к/okak-YYYYMMDDTHHMMSSZ.tar.gz
cd timetable-system/deploy
./deploy.sh init
# Если переносите расписание, выполните ДО первого up:
./deploy.sh import-staff /путь/к/staff.sqlite server
./deploy.sh up server
```

Строку `import-staff` пропустите для чистой установки. Для нового сервера генерируется
новый секрет; оба приложения получают его автоматически. Если восстанавливаете
полную прежнюю установку, можно вернуть её `deploy.env` как `deploy/.env` вместо `init`.

Caddy получит сертификаты после того, как DNS указывает на сервер и порты доступны.
В режиме `server` cookie сотрудников всегда Secure. **Не используйте локальный
режим для публичного сервера.**

Если не перенесли учётную запись:

```bash
./deploy.sh user admin server
```

Зайдите на `https://app.okak.asia` и опубликуйте расписание. Оно появится на
`https://okak.asia`. Никаких ручных настроек ключей между контейнерами не требуется.

## Управление

```bash
./deploy.sh status          # состояние локальных контейнеров
./deploy.sh logs            # логи, завершение просмотра Ctrl+C
./deploy.sh down            # остановить; БД остаются в volumes
./deploy.sh up              # запустить или пересобрать после изменений
./deploy.sh backup          # резервная копия
```

Для сервера добавьте `server` последним аргументом. На обновлении сохраняйте
`deploy/.env` и имя проекта. `up` пересобирает образы и применяет изменения без
сброса БД. **Не используйте `docker compose down -v` и не удаляйте volumes**,
если нужны сохранённые данные. Старые volumes от отдельного UTB2 тоже не удаляйте
до проверки переноса.

## Восстановление студенческого дампа

В новую пустую установку (до первого запуска API) можно восстановить `students.dump`
из `backup` либо дамп прежнего UTB2 в формате `pg_dump -Fc`. Из папки `deploy`:

```bash
# Сначала init и, при необходимости, import-staff. Запускаем только БД:
docker compose --env-file .env -f compose.yaml -f compose.server.yaml up -d --wait student-db
# Восстанавливаем только в ПУСТУЮ БД, одной транзакцией:
docker compose --env-file .env -f compose.yaml -f compose.server.yaml exec -T student-db \
  pg_restore --exit-on-error --single-transaction --no-owner --no-privileges -U okak -d okak < /путь/к/students.dump
./deploy.sh up server
```

Для локального восстановления замените `compose.server.yaml` на `compose.local.yaml`.
Старую официальную студенческую БД восстанавливайте вместе с соответствующей
SQLite сотрудников: источник и номера публикаций должны совпадать.

### Просмотр преподавателями

На общем сайте доступны режимы «Студент» и «Преподаватель». После обновления обоих API сотруднику нужно нажать «Опубликовать», чтобы передать справочник преподавателей и их занятия. Преподаватель выбирает себя по имени, видит время, предмет, аудиторию и все группы общей пары. Редактирование доступно только сотрудникам. При обновлении база автоматически получает новую таблицу опубликованных преподавателей; существующие данные сохраняются.

### Статистика посещений

Панель: `https://app.okak.asia/admin` (локально `http://localhost:8081/admin`). Вход — существующей учётной записью сотрудников. Доступ выдаётся отдельно, не всем сотрудникам автоматически:

```sh
./deploy.sh admin admin local
# На сервере:
./deploy.sh admin admin server
```

Первый `admin` — команда, второй — логин. Для отзыва: `docker compose --env-file .env -f compose.yaml -f compose.local.yaml exec staff-api python manage_admin.py ЛОГИН --revoke` (на сервере заменить `compose.local.yaml` на `compose.server.yaml`).

Статистика хранится в PostgreSQL студентов и входит в резервную копию `students.dump`. Право администратора — в SQLite сотрудников (`staff.sqlite`). Новые таблицы создаются автоматически при старте; публикация расписания не очищает статистику.

Сбор начинается после обновления; прошлые посещения не восстанавливаются. Случайный идентификатор браузера позволяет приблизительно считать посетителей; новый визит начинается после 30 минут без зарегистрированных действий. Фоновые обновления не добавляют просмотры. Do Not Track / Global Privacy Control отключают отправку. В аналитике нет IP, имён посетителей, полных User-Agent или URL: сохраняются категории устройства/браузера и домен источника. События старше 180 дней удаляются при приёме новых событий; отчёты ограничены последними 180 днями. Данные приблизительные: события могут блокироваться или подделываться.

Публично разрешён только приём событий. Отчёт доступен по внутренней сети с ключом публикации и через API сотрудников с проверкой права администратора. После изменения `nginx-student.conf` выполните `./deploy.sh up local` (или `server`), чтобы перечитать конфигурацию прокси.
