# Студенческое расписание UTB2

Для совместного запуска с кабинетом сотрудников используйте
`../timetable-system/deploy/deploy.sh` — полная инструкция находится в
`../timetable-system/deploy/README.md`. Это основной вариант для okak.asia.
Описанный ниже отдельный Compose сохранён для прежнего самостоятельного запуска.

Студенты выбирают группу и день недели. Единственный источник групп и пар —
публикация из `timetable-system`. Telegram-бот и API редактирования старост
удалены. Студенческий сайт не требует авторизации и не умеет изменять расписание.

## Связь с системой сотрудников

В `backend/.env` укажите `PUBLISH_SECRET_KEY` — тот же случайный секрет длиной
не менее 32 символов, что в `timetable-system/backend/.env`. Используйте отдельный
новый ключ, не старый ключ бота. Пример окружения — `backend/.env.example`.
Секрет остаётся только на серверах; не задавайте его через `VITE_*` и не коммитьте.

В системе сотрудников задайте полный `STUDENT_PUBLISH_URL`:

- локально: `http://127.0.0.1:8001/api/v1/publication`;
- на сервере: `https://ВАШ-ДОМЕН/api/v1/publication`.

Публикация передаёт полный список групп, включая группы без пар, и всё расставленное
расписание. Данные заменяются одной транзакцией PostgreSQL. При ошибке до фиксации
предыдущая версия остаётся целиком. Повторная доставка той же версии безопасна;
устаревшие версии и другой источник отклоняются. Если ответ потерялся после фиксации,
сотрудники увидят «не подтверждено» и могут повторно опубликовать текущий черновик.

При первой публикации старое ручное расписание заменяется полностью. Группы
с точно совпадающими названиями сохраняют прежние ID (в том числе для iOS).
Далее связь идёт по постоянному UUID: переименование сохраняет ID, удаление группы
удаляет и её пары, новая группа получает отдельный ID. Не создавайте новую группу
вместо переименования, если хотите сохранить старые ссылки. Не пересоздавайте
рабочую БД сотрудников — там хранится идентификатор источника и номера версий.

До первой публикации сайт показывает «Расписание ещё не опубликовано». После
публикации видна дата обновления; открытый сайт обновляет список и пары раз в
минуту, при возвращении на вкладку и восстановлении соединения. Если выбранная
группа удалена, предлагается выбрать другую. Без сети показывается ошибка;
расписание больше не выдаётся из старого офлайн-кэша. Статика PWA остаётся доступна.
Обои iOS кэшируются по содержимому, поэтому публикация меняет картинку автоматически.

## Запуск

Сохраните резервную копию PostgreSQL перед первым переходом. Новые таблицы
создаются при старте; старые профили старост не удаляются, но API к ним отключён.

```bash
docker compose up -d --build --remove-orphans
```

`--remove-orphans` убирает старый контейнер бота. Не используйте `down -v` —
это удалит том БД. API доступен на порту 8001 (переменная `STUDENT_API_PORT`),
сайт — на 8080. Внутри Docker Nginx по-прежнему обращается к `backend:8000`.
Существующий `.env` должен содержать ваши реальные настройки PostgreSQL.

Для Vite: `cd frontend && npm install && npm run dev`; `/api` проксируется
на `127.0.0.1:8001`. По умолчанию production-фронтенд использует `/api/v1` того же
домена. Если задан `VITE_API_URL`, проверьте, что он указывает на ваш UTB2 backend.
На сервере настройте HTTPS. Endpoint публикации требует Bearer-ключ, обычное
чтение — нет. Для большой публикации настройте лимит тела запроса reverse proxy
(например, Nginx `client_max_body_size 20m;`).

## Проверки

Сквозной тест двух приложений находится в соседнем `timetable-system`:

```bash
cd ../timetable-system/backend
.venv/bin/pip install -r requirements-integration.txt
.venv/bin/python test_publication.py
```

Тест по умолчанию создаёт временные SQLite БД, не меняя рабочие данные.
`UTB_PROJECT_DIR` позволяет указать другое расположение UTB2. Для проверки ветки
PostgreSQL задайте `STUDENT_TEST_DATABASE_URL` на **отдельную пустую тестовую БД**;
тест создаёт и изменяет её таблицы. Никогда не указывайте рабочую БД.
